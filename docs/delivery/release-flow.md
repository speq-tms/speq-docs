# Release flow

Единый процесс доставки изменений для всех репозиториев экосистемы SPEQ, включая `speq-docs`.
Это канонический документ: `CLAUDE.md` в репозиториях ссылаются на него и не дублируют правила целиком.

---

## Единый трекер

**Все issue экосистемы заводятся в [`speq-tms/speq-docs`](https://github.com/speq-tms/speq-docs/issues)** — независимо от того, в каком репозитории окажется код.

Причина: работа регулярно затрагивает два-три репозитория сразу. Issue, заведённый в репозитории кода, теряет остальные части задачи, и расхождение между репозиториями остаётся невидимым — ровно так контракты разъехались с рантаймом к v1.0.0.

Целевой репозиторий задачи определяется:

- меткой `area/*` — `area/cli`, `area/contracts`, `area/examples`, `area/runner`, `area/docs`, `area/release`;
- явным указанием в теле issue.

Метки: `type/*` (bug, feature, docs, chore), `area/*`, `status/*` (blocked, needs-decision), `priority/*` (p0, p1, p2), `epic` для трекинг-issue.

---

## Инвариант: имя RC-ветки совпадает с названием майлстоуна

Майлстоун `v1.1.0` в трекере ⇔ ветка `v1.1.0` в каждом затронутом репозитории.

Это делает поиск RC механическим: узнав майлстоун issue, вы знаете имя ветки, от которой работать.
Майлстоун `backlog` — не релиз и RC-ветки не имеет.

---

## Как определить текущий RC

Источник правды — состояние GitHub, а не этот файл. Проверяйте командой:

```bash
# открытые майлстоуны трекера; имя майлстоуна = имя RC-ветки
gh api repos/speq-tms/speq-docs/milestones \
  --jq '.[] | select(.state=="open" and .title != "backlog") | .title'

# есть ли RC-ветка в целевом репозитории
git ls-remote --heads origin 'v*'
```

**Открытым должен быть ровно один майлстоун-релиз** (не считая `backlog`). Если открытых несколько — значит, выпущенный майлстоун забыли закрыть, и автоопределение RC даст неверный ответ. Закрывайте майлстоун в момент публикации релиза, вместе с тегом.

Если RC-ветки в целевом репозитории нет — её ещё не открывали. Создать от `main`:

```bash
git push origin origin/main:refs/heads/<RC>
```

> **Осторожно со `speq-cli`.** Его `.github/workflows/release.yml` реагирует на мерж в `main` PR, у которого имя head-ветки начинается с `v`, и запускает сборку и публикацию релиза. Не открывайте там RC-ветку ради мелкого изменения, которое не должно приводить к релизу.

## Рабочий цикл

1. **Взять issue** из открытого майлстоуна в `speq-tms/speq-docs`.
2. **Определить целевой репозиторий** по метке `area/*`.
3. **Убедиться, что в нём есть RC-ветка** с именем майлстоуна.
4. **Создать delivery-ветку от RC — не от `main`:**

   ```bash
   git fetch origin
   git switch -c docs/dsl-reference origin/v1.1.0
   ```

   Именование: `feat/<scope>-<name>`, `fix/<scope>-<name>`, `chore/<scope>-<name>`, `docs/<scope>-<name>`.

5. **Коммитить в стиле Conventional Commits.**
6. **Открыть PR в RC-ветку**, не в `main`:

   ```bash
   gh pr create --base v1.1.0 --title "docs: add DSL reference" \
     --body "Part of speq-tms/speq-docs#10"
   ```

7. **Связать с issue вручную.** Ключевые слова GitHub (`Closes`, `Fixes`) срабатывают **только при мерже в ветку по умолчанию**. В этом процессе PR всегда идёт в RC-ветку, поэтому ключевое слово не срабатывает **никогда и ни в одном репозитории**, включая сам `speq-docs`. В PR пишите `Part of speq-tms/speq-docs#10`, а после мержа закрывайте issue сами:

   ```bash
   gh issue close 10 --repo speq-tms/speq-docs \
     --comment "Landed in speq-tms/speq-contracts#<PR>."
   ```

   Предупреждения не будет: ключевое слово просто игнорируется, issue тихо остаётся открытым, и это
   обнаруживается позже по расхождению счётчика в майлстоуне. Единственный PR во всём процессе, где
   ключевое слово сработало бы, — финальный мерж RC в `main`, но к тому моменту все issue уже закрыты.

8. **Отметить чекбокс** в теле epic-issue, если задача входит в эпик.
9. Когда все issue майлстоуна закрыты — **один финальный PR из RC в `main`** по каждому затронутому репозиторию, затем тег.

## Единственное исключение: не-релизное содержимое

Файлы, которые не входят в поставляемый артефакт — `CLAUDE.md`, правила для агентов, конфигурация редактора, — доставляются веткой `chore/*` напрямую в `main`, если в репозитории нет открытой RC-ветки.

Причина: открывать RC ради правки инструкции для агентов дороже, чем нарушить правило. В `speq-cli` это ещё и опасно — мерж RC в `main` опубликует релиз (см. предупреждение выше).

Исключение **не** распространяется на код, схемы, примеры, формулы и workflow-файлы. Всё, что влияет на поведение или на поставляемый артефакт, идёт через RC.

## Правила ветвления

1. Не доставлять фичи и фиксы напрямую из `main`.
2. Создать release-candidate ветку от `main` — например `v1.1.0` или `v1.1.0-alpha.1`.
3. Создавать delivery-ветки **только от RC**.
4. Открывать PR из delivery-ветки в RC.
5. По готовности открыть один финальный PR из RC в `main`.
6. Использовать Conventional Commits в сообщениях коммитов и заголовках PR.

Если блокер найден до публикации тега — исправление остаётся в той же RC-ветке. Если тег уже опубликован —
исправление идёт через новый patch или новую RC.

## Conventional Commits

| Префикс | Когда |
| --- | --- |
| `feat:` | Новое поведение runtime или новая возможность DSL |
| `fix:` | Исправление некорректного поведения |
| `chore:` | Инфраструктура, зависимости, служебные изменения |
| `docs:` | Изменения только в документации |
| `refactor:` | Изменение структуры кода без изменения поведения |
| `test:` | Изменения только в тестах |

## Отчёт по RC

Состав релиз-кандидата не пишется руками — он выводится из состояния GitHub:

```bash
scripts/rc-report.sh            # текущий открытый RC
scripts/rc-report.sh v1.1.0     # конкретный RC
scripts/rc-report.sh v1.1.0 -   # в stdout, без записи файла
```

Отчёт попадает в `docs/delivery/rc/<RC>.md` и содержит: состав по issue майлстоуна, фактически смерженные в RC PR по каждому репозиторию, порядок выката и релизные гейты. Перегенерируйте его после каждого смерженного PR и перед финальным мержем RC в `main`.

Порядок выката — цепочка зависимостей, а не предпочтение: `speq-contracts` → `speq-cli` → `speq-examples` → `speq-github-runner` → `homebrew-tap` → `speq-docs` → `speq-tms.github.io`. `homebrew-tap` нельзя мержить раньше, чем опубликован артефакт релиза `speq-cli`.

## Acceptance gates

Перед мержем RC в `main`:

- `cargo build && cargo test` в `speq-cli` — зелёные;
- прогон `speq-examples/test-repo-mode-jsonplaceholder` даёт `"failed": 0`;
- каждая новая фича покрыта хотя бы одним acceptance-примером в `speq-examples`;
- документация в `speq-docs` описывает фактическое поведение изменённого кода;
- при изменении DSL синхронизированы `speq-cli`, `speq-contracts` и `speq-vscode-extension`.
